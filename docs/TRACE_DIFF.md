# QEMU Trace-Diff Oracle & Boot Contract Documentation

This document describes the execution divergence oracle between the Path N AArch64 emulator and upstream QEMU (v10.1.0), including the comparative boot contracts, diff-noise risks, and instructions for regenerating traces and running the differ.

---

## 1. Boot Contract Comparison: Path N vs. QEMU

| Parameter | Path N Emulator (`u12-orchestrator`) | QEMU (`qemu-system-aarch64 -M virt`) |
| :--- | :--- | :--- |
| **Kernel Binary** | `/mnt/sdb1/aosp/Image` (Linux 4.19.130 AOSP build 6640132) | `/mnt/sdb1/aosp/Image` (identical image) |
| **Physical RAM Base** | `0x4000_0000` | `0x4000_0000` |
| **Physical RAM Size** | `128 MiB` (`0x4000_0000 .. 0x4800_0000`) | `512 MiB` (`0x4000_0000 .. 0x6000_0000`) |
| **Kernel Load Address** | `0x4000_0000` (raw copy from offset 0 of RAM) | `0x4008_0000` (`RAM_BASE + text_offset`, 512 KiB offset) |
| **Entry Point PC** | `0x4000_0000` | `0x4000_0000` (QEMU boot stub), jumps to `0x4008_0000` |
| **Initial SP** | `0x4800_0000` (`RAM_TOP`) | `0x0000_0000` (architectural EL1 reset state) |
| **Initial PSTATE** | `0x0` (all flags clear, EL1) | `0x400003c5` (`-Z--`, DAIF masked, EL1h) |
| **Device Tree (DTB)** | None (`X0 = 0x0`) | Auto-generated by `virt` at `0x4800_0000` (`X0 = 0x4800_0000`) |
| **Initial Registers** | `X0..X30 = 0x0` | `X0 = 0x4800_0000`, `X4 = 0x4008_0000`, `X1..X3 = 0x0` |
| **Machine Model** | Path N Custom: PL011 MMIO at `0x09000000`, GPU MMIO at `0x0A000000` | ARM Virt: GICv2/v3 at `0x08000000`, PL011 at `0x09000000`, virtio-mmio at `0x0A000000+` |
| **Clock / Timer** | Synthetic injected cycle tick (`TIMER_CYCLES_PER_STEP = 1000`) | QEMU TCG simulated architectural virtual timer (`cntvct_el0`) |

## 2. Known Mismatches & Diff-Noise Risks

### Risk 1: Kernel Load Address Offset (`0x80000`)
- **Phenomenon**: The Linux ARM64 kernel header specifies `text_offset = 0x80000` (512 KiB). QEMU complies with the ARM64 boot specification (`Documentation/arm64/booting.rst`) and loads the kernel code at `0x4008_0000`. In contrast, Path N places the image at `0x4000_0000`.
- **Impact**: All virtual and physical addresses inside the kernel differ by exactly `0x80000` (512 KiB). For example, kernel entry `stext` is at `0x413c_0000` in Path N, but at `0x4144_0000` in QEMU.
- **Handling**: `scripts/trace_diff.py` automatically detects this offset (`0x80000`) and aligns Path N PC with QEMU PC.

### Risk 2: Missing DTB Pointer (`X0`)
- **Phenomenon**: QEMU sets `X0 = 0x4800_0000` pointing to the hardware device tree blob. Path N starts with `X0 = 0`.
- **Impact**: At step 3 (`stext + 0x20`, `preserve_boot_args`), the kernel executes `mov x21, x0` to preserve the bootloader argument. In Path N, `X21` becomes `0`, whereas in QEMU, `X21` becomes `0x4800_0000`. When the kernel later accesses device tree nodes or boots devices, memory accesses will diverge completely.

### Risk 3: Initial SP and PSTATE
- **Phenomenon**: Path N initializes `SP = 0x4800_0000` (RAM top) and `PSTATE = 0`. QEMU sets `SP = 0` and `PSTATE = 0x400003c5` (Z flag set).
- **Impact**: Conditional branch decisions relying on initial flags or stack pointers will diverge if checked prior to explicit kernel initialization. (Note: the kernel quickly sets its own stack and flags).

### Trustworthiness Assessment
> [!WARNING]
> Because Path N and QEMU have fundamentally different machine models (lack of DTB in Path N, load offset differences, and differing peripheral models), **blind register-level comparison across the entire run is NOT trustworthy for identifying correctness**.
> 
> However, the oracle IS trustworthy for:
> 1. Verifying instruction-by-instruction execution flow along early setup routines before device tree inspection.
> 2. Comparing pure arithmetic and logical transforms (`ADD`, `SUB`, `ORR`, `CLZ`, `MADD`, bitfields) against golden TCG behavior.
> 3. Diagnosing whether a divergence is an emulation bug (wrong opcode evaluation) versus an architectural machine-model mismatch (boot arguments / memory layout).

## 3. Reproduction & Execution Commands

### Step A: Regenerate QEMU Trace
Run QEMU with a short timeout (3–5 seconds produces thousands of instructions, sufficient for diffing):

```bash
export LD_LIBRARY_PATH=/home/muse/qemu-root/usr/lib/x86_64-linux-gnu
timeout 5s /home/muse/qemu-root/usr/bin/qemu-system-aarch64 \
  -M virt -cpu cortex-a57 -m 512 \
  -kernel /mnt/sdb1/aosp/Image -nographic -net none \
  -L /home/muse/qemu-root/usr/share/qemu \
  -accel tcg,one-insn-per-tb=on -d cpu -D target/qemu_cpu_raw.log </dev/null || true

# Extract head slice (e.g. first 24,000 lines = 2,000 instructions)
head -n 24000 target/qemu_cpu_raw.log > target/qemu_trace.log
rm -f target/qemu_cpu_raw.log
```

### Step B: Regenerate Path N Trace
Run `run_kernel` with the `--trace` flag:

```bash
cargo run -p u12-orchestrator --bin run_kernel -- --max-steps 2000 --trace target/pathn_trace.log
```

### Step C: Run the Trace Differ

1. **Standard differ with auto-detected kernel load offset (`0x80000`)**:
   ```bash
   python3 scripts/trace_diff.py --qemu target/qemu_trace.log --pathn target/pathn_trace.log
   ```

2. **Differ with boot-contract register ignoring (`--ignore-boot-regs` filters X0, X21, SP, NZCV)**:
   ```bash
   python3 scripts/trace_diff.py --qemu target/qemu_trace.log --pathn target/pathn_trace.log --ignore-boot-regs
   ```

3. **Differ with raw PC matching (no offset adjustment)**:
   ```bash
   python3 scripts/trace_diff.py --qemu target/qemu_trace.log --pathn target/pathn_trace.log --pc-offset 0
   ```
