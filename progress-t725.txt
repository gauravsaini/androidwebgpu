## Step 2b — Minimal-file design (recorded before build)
- RULINGS from evidence (each with its proof):
  (1) toybox sh is NOT proven available: strings on the guest toybox binary
      show applets echo/test but no standalone "sh"; ZERO stock .rc files
      use "toybox sh"; hw/init.rc contains 0 "toybox" mentions. Per
      PATTERN-PROOF the marker does NOT depend on sh.
  (2) Persistent-file marker (shape b) is IMPOSSIBLE in this setup: the QEMU
      command line has NO userdata drive; /data lives on the brd ramdisk
      (brd.rd_nr=1 brd.rd_size=524288) and does not persist; system is
      mounted readonly. So the marker MUST be a kmsg line (shape a).
  (3) Marker mechanism: init builtin `write /dev/kmsg T725_REG_OK\n` where
      `\n` is the tokenizer backslash escape (README: "c-style backslash
      escapes may be used to insert whitespace into a token") -- the token
      carries a real newline, so write(2) delivers a complete kmsg line.
      No shell, no toybox, no /data. Even if the escape were literal, the
      marker text still lands in the UART (partial line flushes later) and
      the Command line still logs -- the design is robust to that question.
  (4) The service needs no binary behaviour: init logs
      `starting service 't725probe'` when it starts, and
      `Command 'start t725probe' ...` when the action runs. The service runs
      /system/bin/toybox echo T725_SERVICE (toybox + echo both proven
      present; output to /dev/null is fine -- the start lines are the
      markers).
  (5) T724 queue-stall confounder: in T724 only the FIRST boot_completed
      action (1224) processed; dmesgd/wifi boot_completed actions did not
      (T723: bootstat:67 at 518.2 s + dmesgd:4 at 518.6 s DID process). So a
      single boot_completed action could be starved even if registered.
      MITIGATION: the file carries the SAME marker on TWO triggers --
      `on boot` (~95 s, flood window, may survive) and
      `on property:sys.boot_completed=1` (~498 s, post-flood). A marker at
      ~95 s proves registration via the boot path; at ~498 s via the
      boot_completed path; either is a PASS. Built-in control: check in the
      flight whether stock dmesgd/wifi boot_completed actions processed --
      if they did and mine did not, the failure is file-specific (strong
      FAIL); if neither did, the stall is the likelier mechanism (FAIL per
      contract, stall named, successor discriminates).
- FILE: /system/etc/init/t725probe.rc (NEW; base image revert 0ba6d6d3, so
  the minimal file is the ONLY addition):
    # T725: minimal .rc registration probe. One service + two actions, one marker.
    # The service starts on sys.boot_completed=1 (~498 s, post-flood); the on boot
    # action writes the same marker early (~95 s, flood window) as a second chance
    # if the boot_completed multi-action dispatch stalls (T724 precedent: only
    # the first boot_completed action processed).
    service t725probe /system/bin/toybox echo T725_SERVICE
        class main
        user root
        group root
        oneshot
        disabled

        start t725probe
        write /dev/kmsg T725_REG_OK\n
    <blank>
    on boot

  verified byte-exact with od before the build.)
